AgentForge · 첫 화면 설계 결정 · 2026-08-13

첫 화면은 누구의 화면인가

네 개의 안은 색이 아니라 누구를 우선하는지가 다릅니다. 그래서 정보구조·탐색·밀도· 동선·빈 상태·구현비용이 모두 갈립니다. 와이어프레임은 전부 단색이고, 각 안이 달라지는 영역만 파랗게 칠했습니다 — 네 개를 훑으면 차이점에 눈이 먼저 갑니다.

현재 기준선

지금 / 화면은 정적입니다. 영어 마케팅 문구 한 줄, 고정 카드 3개(RBAC+ACL / Cited / On-prem), 그리고 하드코딩된 “Live” 배지 5개. 실제 데이터가 하나도 없어서 매일 쓰는 지식관리자에게 줄 것이 없고, 처음 온 사람에게도 무엇을 클릭해야 하는지 안 알려줍니다.

네 개 시안

시안 A

작업 대기열

우선 사용자 → 지식관리자(매일)

// 파란 영역 = 처리해야 할 일 목록

정보구조
마케팅 문구 없음. 첫 화면이 곧 할 일 목록 — 색인 실패, 오늘 거부된 질의, 최근 ACL 변경.
핵심 동선
문제를 본다 → 클릭 → 그 문서/실행 화면에서 고친다. 클릭 1회.
밀도
높음. 한 화면에 항목 6~10개.
빈 상태
“지금 처리할 일이 없습니다” + 지난 7일 요약. 빈 화면이 곧 좋은 소식.
접근성
단일 목록이라 키보드·스크린리더에 가장 단순. 건수는 live region으로 알림.
구현 비용
중 집계 API 신규
위험
실패 건수를 세는 엔드포인트가 없습니다 — 프리즈 하에서 Work Order 필요.

시안 B

역할별 입구

우선 사용자 → 처음 온 사람 전원

// 파란 카드 = 내 권한으로 되는 것
// 흐린 카드 = 왜 안 되는지 설명

정보구조
의도별 큰 카드 3개 — 질문하기 / 문서 관리 / 감사·평가. 사이드바도 역할에 맞게 줄어듭니다.
핵심 동선
“나는 무엇을 하려는가”를 고른다 → 그 화면으로. 클릭 1회.
밀도
낮음. 큰 타깃 3개.
빈 상태
빈 상태가 없습니다. 대신 권한 없는 카드를 그 자리에서 설명 — 나중에 403을 맞지 않습니다.
접근성
타깃이 크고 적어 모바일·처음 사용자에 가장 유리. 비활성 카드도 읽어줍니다.
구현 비용
낮음 기존 isPrivileged 재사용
위험
매일 쓰는 사람에게는 클릭이 한 번 늘어납니다. SSO 전에는 역할이 데모 선택입니다.

시안 C

증거 대시보드

우선 사용자 → 파일럿 결정자·방문자

// 파란 영역 = 집계 수치와 추이 차트

정보구조
거버넌스 주장을 뒷받침하는 수치 — 인용률, 거부율, ACL 차단 건수, 감사 이벤트, 최근 평가.
핵심 동선
수치 → 클릭 → 그 수치를 만든 실제 트레이스. 주장과 증거가 이어집니다.
밀도
높음. 타일 + 차트.
빈 상태
“아직 실행 데이터가 없습니다” + 데모 시나리오 실행 버튼.
접근성
차트마다 동등한 표를 제공해야 합니다 — 안 하면 이 안이 가장 취약합니다.
구현 비용
높음 집계 + 차트
위험
이번 주에 확인한 실패 유형 그대로입니다 — 납치된 답변 옆에 초록 배지 4개가 떠 있었습니다. 초록 숫자판은 과신을 만듭니다.

시안 D

되는 것 / 안 되는 것

우선 사용자 → 외부 검토자·감사

// 파란 열 = 아직 안 되는 것 + 근거 링크

정보구조
두 열. 왼쪽은 지금 동작하는 것, 오른쪽은 SSO 미연동·인젝션 미방어·운영통제 미결 — ADR과 Work Order로 링크.
핵심 동선
신뢰를 먼저 만들고 문서로 보냅니다. 작업 동선은 아닙니다.
밀도
중간. 목록 두 개.
빈 상태
빈 상태 없음. 내용이 SSOT에서 옵니다.
접근성
순수 텍스트·목록이라 네 안 중 가장 견고합니다.
구현 비용
낮음 SSOT 파싱 또는 상수
위험
매일 쓰는 사람에게 아무 작업도 주지 않습니다. 첫 화면 전체를 여기 쓰기엔 아깝습니다.

권고

B를 지금, A를 다음에. C는 지금 하지 않기.

B(역할별 입구)를 먼저 하는 이유는 세 가지입니다. 새 API가 필요 없고 (isPrivileged가 이미 있습니다), 수치를 만들어내지 않으므로 피처 프리즈 하에서 순수 UX 변경으로 통과하며, 지금 가장 큰 실제 문제 — 처음 온 사람이 무엇을 클릭할지 모른다 — 를 바로 없앱니다. 권한 없는 카드를 그 자리에서 설명하는 것도 실질적입니다: 지금은 눌러 보고 나서 403을 맞습니다.

A(작업 대기열)가 최종 형태라고 봅니다. 이 제품의 매일 사용자는 지식관리자이고, 그들에게 첫 화면은 “할 일이 있는가”여야 합니다. 다만 실패 건수·거부 건수를 세는 집계 엔드포인트가 없어서 코드 작업이며, 프리즈 하에서는 Work Order가 필요합니다. B 다음 순서로 두는 게 맞습니다.

C는 지금 만들면 안 된다고 봅니다. 근거는 이번 주 측정입니다. 프롬프트 인젝션에 납치된 답변 옆에 배지 네 개가 전부 초록색으로 떠 있었고 그중 하나가 “그라운딩 가드 통과”였습니다. 집계 초록 숫자판은 정확히 그 과신을 화면 전체로 확대합니다. 통제가 실제로 검증되기 전에 증거 대시보드를 만들면, 그 대시보드가 틀렸을 때 아무도 모릅니다.

D는 독립된 화면이 아니라 한 줄로 접습니다. 어느 안을 골라도 첫 화면 하단에 “아직 안 되는 것 3가지 →” 링크 한 줄이면 D의 값어치는 대부분 확보됩니다. 첫 화면 전체를 한계 고백에 쓰는 것은 매일 사용자에게 손해입니다.

포기한 대안과 이유

  • C 단독 — 구현 비용이 가장 높은데, 통제 검증 전에는 과신을 키웁니다. 통제가 증명된 뒤에 재검토.
  • D 단독 — 접근성과 정직성은 최고지만 작업 동선이 0입니다.
  • A 먼저 — 방향은 맞지만 신규 집계 API가 프리즈 예외 사유가 되지 못합니다.
  • 현재 화면 유지 — 하드코딩된 “Live” 배지 5개는 실제 상태를 반영하지 않습니다. 이번 주에 정정한 과장 표현과 같은 유형입니다.
